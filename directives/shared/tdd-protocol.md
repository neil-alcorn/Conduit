## TL;DR
- **Applies to Stage 3 and any behavior-changing code.** Red → Green → Refactor: failing test first, minimum code to pass, clean up with tests green.
- **A test that has never been red proves nothing.** Never write tests after the code (exception: bug fixes — fix first, then a regression test that fails when the fix is reverted).
- **Conventions:** `node:test` only (no Jest/Vitest/Mocha), `tests/[module].test.ts`, `node:assert/strict`.
- **Skips:** config, docs-only, generated code. If unsure, TDD applies. Avoid testing implementation details, mocking internals, skipping refactor.

# TDD Protocol

## Purpose

Enforce test-first development at implementation stages. Tests written before
code serve as executable specifications — they define what "correct" means
before the implementation exists.

---

## When This Directive Applies

- Stage 3 implementation work
- Any code change that modifies observable behavior
- New features, new endpoints, new commands, new utilities

---

## The Cycle: Red, Green, Refactor

### Red — Write a failing test

Write a test that describes the expected behavior. Run it. It must fail.

If the test passes before you write the implementation, either:
- The behavior already exists (no code needed — verify and move on)
- The test is wrong (it is not testing what you think)

A test that has never been red has never proven it can catch a failure.

### Green — Write the minimum code

Write the simplest code that makes the failing test pass. No more.

Do not optimize. Do not handle edge cases beyond what the test requires.
Do not add "while I'm here" improvements. Make the test green and stop.

### Refactor — Clean up

With tests passing, improve the code:
- Extract shared logic
- Rename for clarity
- Remove duplication
- Simplify conditionals

Run tests after each refactor step. If a test breaks during refactor, the
refactor changed behavior — undo it and try a different approach.

---

## Test Conventions

These conventions are from Conduit standards and apply to all convoy work:

### Test runner
Node.js built-in test runner (`node:test`). No Jest. No Vitest. No Mocha.

### File location
Tests live in `tests/` directories alongside source:
```
src/
  commands/
    gate.ts
  tests/
    gate.test.ts
```

### File naming
`[module].test.ts` — matches the source file name.

### Test structure
```typescript
import { describe, it } from 'node:test';
import assert from 'node:assert/strict';

describe('gate command', () => {
  it('returns JSON when --format json is passed', () => {
    // Arrange
    const input = { format: 'json' };

    // Act
    const result = formatGateOutput(input);

    // Assert
    assert.equal(typeof result, 'string');
    assert.doesNotThrow(() => JSON.parse(result));
  });
});
```

### Assertions
Use `node:assert/strict`. Prefer specific assertions (`assert.equal`,
`assert.deepEqual`, `assert.throws`) over generic (`assert.ok`).

---

## When to Skip TDD

TDD is the default. These are the narrow exceptions:

| Situation | Approach |
|---|---|
| **Bug fix with obvious cause** | Fix first, then write the regression test. The test must fail when the fix is reverted |
| **Configuration changes** | No behavioral test needed for `.yaml`, `.json`, or env config changes |
| **Documentation-only changes** | No test needed for Markdown, comments, or README updates |
| **Generated code** | If the code is generated by a tool (not an agent), test the generator — not the output |

If you are unsure whether TDD applies, it applies.

---

## Integration with Verification Protocol

TDD produces the evidence that `verification-protocol.md` requires:

- **"Tests pass"** — the green tests are the proof
- **"Acceptance criteria met"** — each criterion should map to one or more tests
- **"No regressions"** — the full suite passing after refactor proves it

When verification asks "show me the evidence," TDD has already created it.

---

## Anti-Patterns

- **Writing tests after implementation**: The test cannot prove it catches failures if the code already exists. Exception: bug fixes (see above)
- **Testing implementation details**: Test behavior (inputs → outputs), not internal method calls. If you refactor and tests break, the tests were coupled to implementation
- **Mocking everything**: Mocks are useful for external dependencies (network, filesystem). Mocking internal modules hides integration bugs. Prefer real objects when feasible
- **One giant test**: Each test should verify one behavior. If a test name contains "and," split it
- **Green without red**: If you never saw the test fail, you do not know it can fail. Run it before writing the implementation
- **Skipping refactor**: Red-Green without Refactor accumulates technical debt. The refactor step is not optional
